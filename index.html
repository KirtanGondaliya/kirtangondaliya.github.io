01

AI Customer Support Assistant · Personal project, in progress

SupportPilot

The AI suggests the reply · a real person always decides what gets sent

app.supportpilot.dev/inbox
UI design

Screens from the SupportPilot design: the inbox, a message with its AI-suggested reply, and the help-documents page. The system behind them is built; the full web app is the next step. Click a screen to enlarge it.

Support teams answer the same questions every day. SupportPilot helps them do it faster. When a customer writes in, the AI sorts the message (what it's about, how urgent it is) and, when the agent asks, writes a suggested reply using the company's own help documents — so answers are accurate, not made up.

How it works

  • Customers never wait for the AI. Their message is saved instantly. The AI works in the background, and if it fails it simply tries again — no message is ever lost.
  • Each company's data stays private. Many businesses can use the same system, but one company can never see another's customers or documents.
  • Teach it with your own documents. A company uploads its help guide as a PDF. Every file is checked first, so broken or fake files are rejected.
  • AI costs are under control. Every AI action is tracked to a fraction of a cent, and each company has a monthly budget it can never go over.

The hard part

Making the AI honest. If the help documents don't contain the answer, the AI doesn't guess — it tells the agent “I don't have information on this”. Every suggested reply also shows which document it came from, so the agent can check it in seconds.

02

Secure Hospital Messaging · Professional work

Endlink

My role: frontend developer · used daily by doctors, nurses, patients and their families

A secure chat app for hospitals. Each hospital gets the app with its own logo and colours, and patients, family members and staff each sign up through their own simple flow. I built the web app that doctors and nurses use during their shifts.

How it works

  • Messages reach the right doctor automatically. When a doctor's shift starts, new patient messages go straight to them. When the shift ends, the messages are handed back so the next doctor can pick them up.
  • Group chats for every team. Different kinds of groups follow their own rules, so the right people see a message without anyone forwarding it.
  • Urgent messages first. Simple filters let busy staff find the messages that matter in seconds.
  • Parents can help their children. A parent or guardian can manage a child's account safely, with their own login — no password sharing.

The hard part

Conversations change hands on their own — when a shift ends, dozens of patient chats move to the next doctor at once. The screen has to update live, and a patient's message must never end up with two doctors, or with nobody.

03

Online Appointment Booking · Backend system

Booking System

Like booking a doctor online · two people can never get the same time slot

slotly.app/book/dr-anjali-mehta
Concept UI

Example screens I designed to show how the system is used: booking a slot, a provider setting their hours, and a customer's bookings. The project itself is the server side that powers screens like these.

The system behind an online booking app — think booking a doctor, salon or consultant. Providers set their weekly working hours, and customers pick a free time slot and book it. I built the part that runs on the server: the rules, the data and the security.

How it works

  • Set your hours once. A provider enters their weekly schedule and the free time slots appear automatically. Change the hours and the slots update — nothing to fix by hand.
  • No double bookings, ever. Even if two people click “Book” at the exact same moment, only one gets the slot. The other is asked to choose another time.
  • Safe logins. When someone logs out, their session is closed for good, so nobody can reuse it.
  • Customers and providers see different things. Each type of user can only do what they're allowed to, and every form is checked before it's saved.

The hard part

Two people booking the same slot at the same second. A simple “is it free? then book it” check isn't enough — both could see it as free. So the database itself enforces the rule “one booking per time slot”, and it can never be broken.

Online Course Marketplace · Backend system

Course Marketplace

Like Udemy · teachers sell courses, students buy and watch them

coursely.app/courses?page=1
Concept UI

Example screens I designed to show how the system is used: the course catalogue, a course page with locked lessons, and a teacher's dashboard. The project itself is the server side that powers screens like these.

The system behind an online learning website. Teachers create courses and lessons, and students browse, buy and watch them, with a record of everything they've bought. I built the server side: accounts, payments records, permissions and the course catalogue.

How it works

  • Teachers and students have their own views. Teachers manage courses; students browse, buy and learn.
  • Teachers only edit their own courses. Nobody can change someone else's course.
  • Fast, even with many courses. The catalogue loads page by page, so it stays quick as it grows.
  • Clear error messages. When something goes wrong, the app always gets a clear, consistent message it can show the user.

The hard part

Anyone can look at a course, but only buyers can watch its lessons. The same course page has to show different things to a visitor, a student who bought it, and the teacher who made it.
