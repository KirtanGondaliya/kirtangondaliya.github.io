01

Multi-tenant AI Helpdesk Copilot · Personal, in active development

SupportPilot

API + workers + RAG designed end to end · AI drafts, a human always sends

A B2B support copilot. Companies push customer tickets in through an API key; their agents work the inbox in SupportPilot. Every ticket is triaged in the background (category, urgency, summary), and agents can ask for a draft reply grounded in the company's own help documents — retrieved with embeddings and pgvector, never invented.

Key decisions

  • AI runs in workers, not requests. The API answers 202 in milliseconds; BullMQ workers do the 2–8 s model calls with retries, permanent-error detection, and a sweeper that re-queues anything stuck.
  • Tenant comes from the token, never the body. Every query — including the vector search — is scoped by workspace_id. A wrong tenant gets 404, not 403, so IDs don't leak.
  • Upload straight to S3, then distrust it. Pre-signed PUT URLs keep file bytes off the server — but they don't enforce size or type, so the API re-checks the real size and the %PDF- magic bytes before indexing.
  • Money is an integer. Every model call (failures too) is logged with cost in micro-dollars, and each workspace has a monthly AI budget the worker enforces.

The hard part

Making a draft honest. If retrieval finds nothing above a similarity threshold, the model isn't called at all — the agent sees “no relevant knowledge” instead of a confident guess. Customer text is treated as data, not instructions, and the model must cite which sources it used; citations are validated against what was actually retrieved.

02

Secure Hospital Messaging · Professional work

Endlink

Frontend engineer · multi-tenant web app used by clinical staff, patients and caregivers

A HIPAA-minded messaging platform where each hospital onboards with its own branding and runs separate onboarding flows for patients, caregivers and coworkers. I built the React + Redux web app on Firebase — the part doctors and nurses actually live in during a shift.

Key decisions

  • Routing follows the on-call schedule. Patient threads auto-assign to whoever is on call when a shift starts, fall back to unassigned when it ends, and move to a resolved queue once closed.
  • Three kinds of groups. Agent, on-call and regular groups each carry different routing rules, so the right people see a message without anyone forwarding it.
  • Urgent first. Priority and to-do filters let clinical staff surface the messages that matter in seconds, not scrolls.
  • Delegated access as a first-class model. A minor patient managed by a parent or guardian account gets role-based, delegated permissions rather than shared logins.

The hard part

Thread ownership changes without anyone clicking anything — a shift boundary moves dozens of conversations at once. The UI has to reflect reassignment live and never show a thread as owned by two doctors, or by nobody, while a patient is waiting.

03

Appointment Booking System · Backend

Booking API

Layered REST API · the database, not the code, guarantees one booking per slot

A scheduling backend where service providers publish weekly availability and users book slots. Built with a clean controller → service → repository split on Bun, Express, TypeScript and Prisma over PostgreSQL.

Key decisions

  • Slots are generated, not stored. Time slots are computed from a provider's weekly availability, so changing hours never leaves stale rows behind.
  • Double-booking is a constraint. A database-level uniqueness rule makes two simultaneous bookings for the same slot impossible — the loser gets a clean 409.
  • Logout that actually logs out. JWTs are blacklisted on logout, and a daily cron job purges expired entries so the table never grows unbounded.
  • Two roles, enforced in middleware. USER and SERVICE_PROVIDER permissions with Zod validation on every input.

The hard part

“Check if the slot is free, then insert” has a gap: two requests can both see it free. Instead of locking in application code, the insert itself is the check — the constraint rejects the second write atomically.

04

Course Selling Platform · Backend

Course API

Marketplace REST API · instructors publish, students buy, both see only what they should

The backend for an online course marketplace: instructors create courses and lessons, students browse, purchase and keep a purchase history. Built on Bun, Express, TypeScript and Prisma with PostgreSQL.

Key decisions

  • Role-based access from the first route. INSTRUCTOR and STUDENT roles gate course and lesson management, purchases and history.
  • Ownership checks, not just role checks. An instructor can only edit the courses they own.
  • Paginated listings. Course catalogues are paged so responses stay small as the catalogue grows.
  • One error shape everywhere. Standardized error handling means every endpoint fails the same predictable way.

The hard part

Keeping lesson content locked until purchase while still letting anyone browse the catalogue — the same course resource has to render differently for a visitor, a buyer and its instructor.
